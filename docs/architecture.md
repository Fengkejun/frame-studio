# 框架边界与下一阶段入口

## 当前结构

`src/app/App.tsx` 负责应用壳与两个页面的切换。页面很少，暂用类型化的本地页面状态；需要项目 URL、深链接或前进后退时再引入路由。

功能代码按 `features` 组织；跨功能的 UI、IPC、类型放在 `shared`。当前没有引入全局状态库、画布引擎、数据库或模型 SDK，以避免提前约束工作流设计。

`src/shared/lib/desktop.ts` 是前端调用 Rust 的集中入口。`get_app_info` 对应 `src-tauri/src/commands/mod.rs`，类型在 `shared/types/desktop.ts`。浏览器预览不调用 Rust；桌面模式才发起真实 IPC。超时只结束前端等待，不意味着取消原生命令。

## 安全与持久化

- Tauri `build.rs` 显式声明命令清单，`capabilities/main.json` 只允许主窗口调用 `get_app_info`。
- 使用系统原生标题栏；不开放自定义窗口控制权限。
- 生产页面不允许任意远程脚本、远程连接和内嵌页面。开发模式单独允许固定 Vite 地址与热更新 WebSocket。
- 只有主题偏好使用 localStorage，存储不可用时仍能使用当前会话。
- 后续模型密钥不能放入 `VITE_*`、前端源代码、localStorage 或普通项目 JSON。接入时另行设计原生凭据存储和服务调用边界。

## 下一任务的建议入口（本次不实现）

1. 在 `features/workflow` 实现工作流编辑页面并启用导航入口；届时再选择画布库、节点端口协议和数据结构。
2. 将素材管理放入 `features/assets`，项目保存由 Rust 原生命令承接，按目录粒度申请权限。
3. 模型调用、任务状态与重试策略在确认工作流协议后引入，避免 UI 组件直接持有供应商密钥。
4. 明确画布编辑状态、项目持久化状态、后台运行状态三者的边界，再决定是否采用全局状态库。

## 验证分层

- `npm run check`：前端类型、规范、格式。
- `npm test`：页面启动、浏览器降级、主题保存与系统主题响应、存储失败恢复。
- `desktop:check` / `desktop:lint`：原生代码与配置检查。
- 本机启动 Tauri 后看到真实版本、平台、架构，并能“重新检查连接”，才算完成原生 IPC 验证。

跨平台配置保留，但只应声称在实际构建和运行过的平台上验证通过。
